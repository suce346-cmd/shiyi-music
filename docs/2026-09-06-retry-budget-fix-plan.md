# 实测链路重试与预算问题修复方案（R1–R5）

> 来源：2026-09-06 App 内四模式实测（Mode D 跑满 15 分钟超时熔断，Mode A 两轮收敛后死在终稿门外）。
> 网关：间歇性 429（直连三次两 429 一 200），另有网络错误、流式解码错误。
> 目标：彻底解决问题，不回避、不简化。动结构，不只调数字。
> 约束：Mimosa 生成前安全约束仅在相关时视为验收条件；凭据只从环境变量或密钥服务读取，源码/示例/测试不写可用凭据字面量；服务端请求仅允许 http/https，发请求前校验 host，拒绝 localhost、环回、私有和保留地址。

## R1：重试退避与业务共用一池，终稿被饿死

- **问题原因**：
  `send_with_retry`（`src-tauri/src/commands/llm.rs:36-96`）的退避等待消耗的是入口定死的共享 deadline。`Budget::with_timeout(timeout)` 在 `src-tauri/src/commands/orchestrator.rs:1006` 以 15 分钟创建，经 `budget.rs:11-13` 定死 deadline，全链路透传。重试无独立配额。Mode D 日志 01:18:11 同一秒四条 30 秒退避、01:30:47 四条连发加一条 60 秒，全部记在 15 分钟总账上。Mode A 死时剩 10 秒，连 `MIN_ATTEMPT_BUDGET`（`llm.rs:42`，15 秒）都过不去，更放不下 429 首次 30 秒退避。
- **有何影响**：
  链路越长死得越早。D（四角色最长链）超时死；A（两轮已收敛，情感转无异议带核查清单，制作剩 1 处，校验员剩 2 处，tokens 106799）死在终稿门外。用户看到“讨论都快完了，最后一步失败”。
- **应该怎么修复**：
  引入终稿保底额度。新增 `FINAL_STAGE_RESERVE = 120 秒`。讨论轮内每次进 `send_with_retry` 前可用预算 = `remaining - RESERVE`，退避等待按 `min(计划等待, 可用)` 自适应截断；进阶段 2（`run_audit_format` 入口）后解除约束，全额使用剩余预算。429 的 30/60 秒、5xx 的 15/30 秒、网络的 10/20 秒阶梯不动，动的是“等不等得满”。
- **旧规则怎么处理**：
  `retry_plan`（`llm.rs:24-31`）阈值保留；`MIN_ATTEMPT_BUDGET` 15 秒保留；`PIPELINE_TIMEOUT` 15 分钟（`orchestrator.rs:951`）保留；B1 `spawn_guarded` 强杀（`orchestrator.rs:965-981`）保留为最后防线。只加保底闸，不删旧逻辑。
- **新规则怎么握手落地**：
  `Budget` 新增 `remaining_for_discussion(reserve)` 方法；`send_with_retry` 的预算检查点（`llm.rs:50`）与退避中断点（`llm.rs:66,83`）改读该值；`run_audit_format`（`orchestrator.rs:791`）入口改回读全额 `remaining`。切换点唯一：阶段 2 入口（`orchestrator.rs:1196`）。
- **修复后的预期**：
  同样抖动下 A 能进终稿完成至少一次完整尝试加 30 秒退避；D 超时前至少把最后一版送进格式输出。
- **怎么验证修复有效**：
  1. 单测：剩余 90 秒进终稿，断言放行且重试等待完整执行。
  2. 集成测：mock 网关连续 429，断言讨论轮等待被截断、终稿仍产出。
  3. 实网：重跑 Mode A 同一输入，对比终稿是否产出、tokens 是否完整。
- **怎么确保关联链路没问题**：
  取消优先于预算（`llm.rs:46`）不动；B1 强杀不动；B4 截断分级不动；前端错误文案新增“预算不足已保留终稿额度”区分项，不混入旧 Timeout 文案。
- **定位**：`src-tauri/src/commands/llm.rs:42,50,66,83`；`src-tauri/src/budget.rs:11-35`；`src-tauri/src/commands/orchestrator.rs:996-1006,1196`。

## R2：流式 body 解码错误零重试，阶段 0 裸奔

- **问题原因**：
  `send_with_retry` 只保“请求发出去”，不保“流读完”。`stream_response`（`llm.rs:332-410`）chunk 解码失败（`llm.rs:364-367`）直接转 `Network` 返回，无重试。Mode A 第一次 118 秒后 `Stream error: error decoding response body` 直接死。
- **有何影响**：
  阶段 0 是全链路最贵的一次调用（A 重试后 60 秒出 3398 字符），失败一次等于整单从头来。网关抖动下流式中断是常态，零重试等于把最贵的步骤放在最脆的位置。
- **应该怎么修复**：
  给 `call_llm_stream`（`llm.rs:255-293`）加整流同参重试一次，复用审改“解析失败同参重试一次”模式（`orchestrator.rs:516-534`）。仅对 `Stream error` 与空正文两种错误重试；429/5xx 仍走原通道，避免双重退避叠加。
- **旧规则怎么处理**：
  `send_with_retry` 不动；取消检查（`llm.rs:357`）、30 秒进度日志（`llm.rs:360`）、尾部行修复（`llm.rs:387`）、空正文禁静默（`llm.rs:394`）保留。“流式错直接抛”改为“记一次 warn 再整流重发一次”，仍失败才抛，文案不变。
- **新规则怎么握手落地**：
  在 `run_host_initial`（`orchestrator.rs:682-718`）内包一层，与 `execute_review` 重试写法对齐。阶段 0 截断直接报错（`orchestrator.rs:711-713`，半截不进讨论轮）与本重试互不干扰：截断是成功返回但 `finish_reason` 异常，重试只针对抛错路径。
- **修复后的预期**：
  A 第一次那种 118 秒解码中断自动再跑一次，用户看到“阶段 0 多花一次时间”而非“整单失败点重试”。
- **怎么验证修复有效**：
  1. 单测 mock 首流 100 秒处断流，断言第二次整流触发且正文完整。
  2. 日志断言一次流式错误 warn 加一次重发。
  3. 实网跑 Mode A 三次，统计阶段 0 一次通过率。
- **怎么确保关联链路没问题**：
  B4 阶段 0 截断报错不动；预算闸门对重发同样生效；前端 `llm-chunk` 单例监听（过期 run 丢弃）不动。
- **定位**：`src-tauri/src/commands/llm.rs:255-293,355-367,393-399`；`src-tauri/src/commands/orchestrator.rs:682-718,516-534`。

## R3：失败全丢，讨论两轮的修订无落盘

- **问题原因**：
  历史只在成功终稿落盘（前端 `history_save`，后端 `history.rs:80-92` 原子写）。`run_pipeline_inner` 任何一步 `?` 抛错直接整单返回（`orchestrator.rs:1140,1156,1178`），`current_plan`、`revisions_log`、`round_changes` 全是内存变量。A 两轮、D 两轮修订失败后只能从头再跑。
- **有何影响**：
  放大 R1 伤害。预算耗尽只丢终稿本可接受，现在连已收敛讨论也丢，用户为抖动付双倍时间。
- **应该怎么修复**：
  新增流水线检查点文件 `pipeline_checkpoint_{run_id}.json`，内容 `{mode, current_plan, revisions_log, round, next_tasks, issues}`。写入点：每次 `DiscussionRound` 发射后（`orchestrator.rs:1181`）、阶段 2 入口（`1196`）、终稿成功后删除。失败时错误附检查点路径，前端出错条加“从上次继续”按钮，调新增 `pipeline_resume` 命令（复用增量 `extract_previous_plan` 起步逻辑 `1092-1100`）。
- **旧规则怎么处理**：
  `history.json` 成功落盘语义不动；检查点独立文件不污染历史；前端 500 毫秒防抖不动。“失败即空手”改为“失败留检查点”，成功路径多一次删除动作。
- **新规则怎么握手落地**：
  后端新增 `commands/checkpoint.rs`（save/load/clear），`lib.rs:30-45` 注册 `pipeline_resume`；前端出错态加按钮，复用增量通道（`refine_targets` 为空即全量续跑）。检查点与 `【上一版方案】` 提取（`orchestrator.rs:909-918`）同一套起步语义，不新增协议。
- **修复后的预期**：
  A 预算耗尽后点续跑，直接从第二轮汇总后方案进终稿；D 超时后同样可续跑。
- **怎么验证修复有效**：
  1. 单测断言每轮 DiscussionRound 后检查点存在且 JSON 可解析。
  2. 杀进程模拟崩溃后调 resume，断言从断点继续。
  3. 实网跑 A 到预算耗尽点续跑，断言终稿产出且增量 tokens 只含终稿部分。
- **怎么确保关联链路没问题**：
  F3 历史迁移哨兵不动；检查点写 `tmp+rename` 原子写（照抄 `history.rs:84-90`）；成功后删除；取消不写检查点，避免复活已取消任务。
- **定位**：`src-tauri/src/commands/orchestrator.rs:1140,1156,1178,1181,1196`；`src-tauri/src/commands/history.rs:80-92`；`src-tauri/src/lib.rs:30-45`；`src/App.tsx` 出错态。

## R4：四角色并发惊群，429 被自己人放大四倍

- **问题原因**：
  讨论轮四角色 `join_all` 并发（`orchestrator.rs:1134-1138`），各进独立 `send_with_retry`。网关一抖，四人同时 429、同时等 30 秒、同时重发。D 日志 01:30:47 同一秒四条 429 为证。第二波又撞一起，退避升到 60 秒，四倍消耗。
- **有何影响**：
  抖动被并发数放大。双角色链（A）可收敛；四角色链（D）同网关下必超。易误判为 D 提示词问题，实为并发重试踩踏。
- **应该怎么修复**：
  1. 退避加抖动：`retry_plan` 返回等待加 0–5 秒随机抖，四人错峰重发。
  2. 同轮 staggered 启动：`execute_review` 分发（`orchestrator.rs:1134`）按角色序号加 `index * 2 秒` 延迟错峰。等待阶梯不动，只加离散。
- **旧规则怎么处理**：
  `retry_plan` 纯函数阈值不动，抖动包在外面，原有单测继续通过；`join_all` 并发与保序收敛测试不动。
- **新规则怎么握手落地**：
  抖动用时间纳秒取模，不引入新配置；stagger 延迟可被取消打断，不阻塞停止。改动限现有函数内，不新增跨文件协议。
- **修复后的预期**：
  四路重发不再同秒齐射，第二波 60 秒退避概率大降，D 总耗时回到 10 分钟内设计区间（`orchestrator.rs:950` 注释）。
- **怎么验证修复有效**：
  1. 单测 mock 同时 429 四路，断言重发时间戳离散度大于 3 秒。
  2. 日志统计同秒 429 条数下降。
  3. 实网跑 Mode D 三次，统计总耗时与超时率。
- **怎么确保关联链路没问题**：
  取消检查在延迟前后各一次；预算中断对延迟同样生效；B2 unwind 约束不动。
- **定位**：`src-tauri/src/commands/llm.rs:24-31,60-72`；`src-tauri/src/commands/orchestrator.rs:1133-1150`。

## R5：测试连接零重试，间歇 429 直接误报失败

- **问题原因**：
  `test_api`（`llm.rs:681-707`）裸 `client.post().send()`，没走 `send_with_retry`。间歇 429 下撞上即显示“连接失败”，用户误以为 key 或网关坏了。
- **有何影响**：
  key 正确时被误导换 key、换网关。测试接口成功判定仅 HTTP 2xx（`llm.rs:698`），本可轻松重试，却把抖动原样暴露给用户。
- **应该怎么修复**：
  `test_api` 改走 `send_with_retry`，配 120 秒独立小预算（不占流水线 15 分钟池）。成功判定与失败分类（401/403 走 Auth，429 走 RateLimit）保留。
- **旧规则怎么处理**：
  `test_api_body` 的 `max_tokens=16`（`llm.rs:667-674`）不动；`build_client(120)` 不动；前端 loading 与徽标逻辑不动。“一次定胜负”改为“最多 3 次定胜负”，文案不变。
- **新规则怎么握手落地**：
  与流水线共用 `retry_plan`，预算函数内新建 120 秒 `Budget`，天然隔离。角色级测试同走该函数一并受益。
- **修复后的预期**：
  间歇 429 下点测试连接，一次等待后自动转成功，不再误报。
- **怎么验证修复有效**：
  1. 单测 mock 首 429 次 200，断言返回成功且只发两次请求。
  2. 实网抖动时段连点五次，成功率升至全过。
- **怎么确保关联链路没问题**：
  测试与流水线预算隔离；仍走 Rust 后端绕 CORS；凭据只从输入框读，不落盘。
- **定位**：`src-tauri/src/commands/llm.rs:665-707`。

## 整体预期与验证顺序

- 同样抖动下 Mode A 一次跑通，Mode D 回到 10 分钟内可完成，失败最多丢终稿不丢讨论，测试连接不再误报。
- 单测先行（抖动、保底门、检查点、离散度、测试重试五组），再实网按 D、A、B、C 顺序各跑一次。B 看三角色收敛，C 看逐行对齐与重试不丢词。
