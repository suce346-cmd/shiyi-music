## 二、架构设计（第二步台账 6/6）

### 2.1 现有模式分析（CONFIRMED，来源：逐行深读）

- 技术栈：Tauri 2 + Rust（后端）+ React 19 + TS（前端），无 ORM/服务端。
- 模块边界：`orchestrator.rs`（流程）/ `roles.rs`（人设）/ `knowledge.rs`（检索渲染）/ `validator.rs`（硬校验）/ `prompts.rs`（模式指令）/ `energy.rs`（能量解析）。
- 抽象层：`inject_knowledge(kb, tables, plan)` 统一注入点；`role_for(role)` 唯一人设源；`validate_for_mode` 唯一硬校验入口。
- 类似功能实现：R1 保底（`remaining_for_discussion`）、R3 检查点（tmp+rename）、R6 座位（`seats_for_mode` 与 `steps_for_mode` 分离）——本方案沿用“新旧语义分离、旧逻辑不动”手法。
- 命名约定：`INJECT_MAX_*` 集中常量；`validate_*` 纯函数可测；错误经 `AppError` 分类。
- 错误处理：预算闸门 + 取消优先 + 降级警示（degraded 不阻断收敛）。

### 2.2 估算先行

- 峰值：同轮 4 并发审改；单 run LLM 调用约 15 次（含重试）；单次注入上限 4500 字 + 方案 8000 字 + 人设数千字，单调用上下文约 1.5 万字。
- 存储：检查点单文件数十 KB；知识库全量 290 行常驻内存（OnceLock）。
- 查询模式：当前为“全文 contains + 能量区间”；目标为“结构化 key（能量/BPM/弧线标签）+ 确定性默认”。
- 占位估算：无（本方案不依赖 UNKNOWN 指标做选型；P50 与成本上限仅影响验收口径，已在基线声明）。

### 2.3 关键技术决策与候选（含最简单方案）

**D1：规则单源（阈值只定义一次）** —— 关键（改变 validator 与 prompt 的接口关系）。

- A（最简单）：手写 `CHECKLIST.md`，人工同步三处，零代码改动。否决： drift 依旧靠人品，与现状同病。
- B（选定）：新建 `rules.rs`，`pub const` 阈值 + `pub fn checklist(mode) -> &'static str`（与常量同文件手写一次）；`validator.rs` 改用 const；`roles.rs` 人设删数字、末尾拼接同文件 checklist。无新依赖，可逆（git revert 单文件）。
- C（最优备选）：运行时规则注册表（结构体数组同时生成校验闭包与 prompt 文本）。否决：当前规则仅十余条，注册表抽象超配；待规则超 30 条时重审。

**D2：角色 prompt 瘦身去重** —— 关键（改变外部可观察行为：prompt 文本）。

- A（最简单）：人工删重复段落。否决：无归属矩阵，下次加功能又长回去。
- B（选定）：先定维度归属矩阵（情感=情绪能量弧线人声；制作=配器流派空间；作词=结构金句可唱性；改词=对齐专项；流行=传播专项；参数区间只归校验员），再按矩阵删跨角色重复，目标 roles.rs 缩减约三分之一。每次只动一个角色，D 模式实网验证。
- C（最优备选）：prompt 碎片模块化组装。否决：6 个角色碎片化后可读性下降，单人维护成本反升。

**D3：检索 key 结构化** —— 关键（改变 `inject_knowledge` 输入语义与兜底行为）。

- A（最简单）：保留 contains，加确定性默认（查不到给模式默认值，不塞随机 3 行）。可接受为过渡，但 key 不可靠的根因仍在。
- B（选定）：key 改为结构化三元组（能量区间来自 `energy.rs`、BPM 来自 `plan_bpm_value`、弧线标签来自主持人输出受控词表 + 解析器），查不到走确定性默认，删除“随机 3 行 + 禁止照搬”自矛盾指令，换成“按功能选一件并说明理由”。
- C（最优备选）：向量/语义检索。否决：引入新依赖与本地索引，与“无新依赖”约束冲突；290 行规模下结构化 key 已够用。

**D4：阶段 0 加地基** —— 关键（改变阶段 0 prompt 内容）。

- A（最简单）：四模式共用一段静态 primer（流派调色板方向 + 能量标尺，数百字）。兜底可用，但模式针对性弱。
- B（选定）：模式专属 primer（A/B：弧线能量标尺；C：对齐铁律三行；D：传播三件套），取材现有表格只读裁剪，每模式上限 800 字。只读不动表。
- C（最优备选）：primer 由 D3 的结构化 key 动态生成。否决：与 D3 耦合，D3 风险最大，不应让阶段 0 等它；待 D3 稳定后可升级。

### 2.5 选定记录

- 决策 D1：选定 B — 单源落到一个文件、测试锁 verbatim，drift 在数学上消失；否决 A（人治）、C（超配）。
- 决策 D2：选定 B — 归属矩阵防复发，分角色小步验证；否决 A（会长回）、C（可读性代价）。
- 决策 D3：选定 B — 零新依赖下把 key 做可靠，删自矛盾指令；否决 A（根因仍在）、C（新依赖）。
- 决策 D4：选定 B — 与 D3 解耦的模式专属地基；否决 A（太泛）、C（等 D3 稳定后再升级）。
- 假设：阈值数值不变（ASSUMED，若用户要调数值，D1 让改数变成改一处）；网关行为延续当前（讯飞 404 秒基线；若大变，D3/D4 重审）。

### 3.2 数据流

```

```

每个 Phase 内每个组件 = 一次 code-rules 五步流程执行单元（诊断→方案→施工→治味→交付）。

## 四、决策记录（第四步台账 3/3）
